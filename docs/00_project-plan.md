# URL短縮サービス プロジェクト計画書

作成日: 2026-10-29

## 1. 概要と目的

長いURLを短いURLに変換し、アクセス時に元のURLへ転送するWebサービスを、Laravel（API）とTypeScript + React（画面）で開発する。

目的は、フルリモートの自社開発企業への転職に向けたポートフォリオ作成である。機能の多さではなく、設計判断の根拠・型安全・テスト・CIといった「品質を担保して作れること」を示すことを重視する。

- 公開（本番リリース）はしない。ローカル環境で動作し、GitHubで公開するコードとドキュメントで評価してもらう
- 費用はかけない（有料APIや有料ホスティングを使わない）

## 2. ゴールと完成の定義

MVP（最小構成の3機能）が動き、以下をすべて満たした時点を「完成」とする。

- [ ] `docker compose up` だけでバックエンド・フロントエンド・DBが起動する
- [ ] URL登録・リダイレクト・一覧表示（クリック数付き）が画面から操作できる
- [ ] バックエンドの静的解析（Larastan）とフロントエンドの型チェック（tsc）がエラーなしで通る
- [ ] 自動テストが通り、GitHub ActionsのCIで静的解析とテストが自動実行される
- [ ] READMEに概要、画面のスクリーンショットまたはGIF、構成図、セットアップ手順、設計判断の理由が書かれている
- [ ] 要件定義書・設計書・テスト設計書がリポジトリの `docs/` に揃っている

## 3. スコープ

MVPは3機能に絞り、完成させてから拡張する。

| 区分 | 機能 | 内容 |
| --- | --- | --- |
| MVP | URL登録 | 長いURLを入力すると短縮コードを発行し、短いURLを返す |
| MVP | リダイレクト | 短いURLへのアクセスで元のURLへ転送し、クリックを記録する |
| MVP | 一覧表示 | 登録済みURLとクリック数を一覧で表示する |
| 将来拡張 | 有効期限 | 期限切れの短縮URLは転送しない |
| 将来拡張 | カスタムコード | 好きな文字列を短縮コードに指定できる |
| 将来拡張 | クリック推移グラフ | 日別クリック数をグラフで表示する |
| 将来拡張 | ログイン | ユーザーごとに自分のURLだけを管理する |

対象外：本番環境へのデプロイ、独自ドメインの取得、アクセス元の詳細分析（地域・端末など）。MVPではログイン機能を持たないため、一覧はローカル環境の全件を表示する。

## 4. 技術スタックとシステム構成

バックエンドはLaravelのAPI、フロントエンドはReact + TypeScriptのSPAとし、1つのリポジトリで管理する。各ツールのバージョンは着手時点の最新安定版で確定し、READMEに記載する。

| 領域 | 採用技術 | 用途 |
| --- | --- | --- |
| バックエンド | PHP / Laravel | REST API、リダイレクト処理 |
| キュー | Laravel Queue（databaseドライバ） | クリック記録の非同期処理 |
| DB | MySQL | 短縮URL・クリックの保存 |
| フロントエンド | React + TypeScript（Vite） | 画面（SPA） |
| API型連携 | OpenAPI（Scramble等で生成）+ openapi-typescript | APIの型をフロントへ自動反映 |
| 静的解析・整形 | Larastan / Laravel Pint / ESLint / Prettier | 型チェック、コード規約 |
| テスト | Pest / Vitest + React Testing Library | バックエンド・フロントエンドの自動テスト |
| 環境 | Docker Compose | ローカル環境の一括起動 |
| CI | GitHub Actions | 静的解析・テストの自動実行 |

リポジトリ構成（案）:

```
url-shortener/
├── backend/      # Laravel
├── frontend/     # React + TypeScript
├── docs/         # 要件定義書・設計書・テスト設計書
├── compose.yaml
└── README.md
```

## 5. API・画面・データの概要

MVPはAPI 3本、画面2つ、テーブル2つで構成する。詳細は各設計書で確定する。

API

| ID | メソッド | パス | 概要 |
| --- | --- | --- | --- |
| API-01 | POST | /api/short-urls | URLを登録し、短縮コードと短いURLを返す |
| API-02 | GET | /api/short-urls | 登録済みURLの一覧とクリック数を返す |
| API-03 | GET | /{code} | 元のURLへリダイレクトし、クリックを記録する |

画面

| ID | 画面名 | 概要 |
| --- | --- | --- |
| SCR-01 | URL登録画面 | URL入力フォーム、発行された短いURLの表示とコピーボタン |
| SCR-02 | URL一覧画面 | 登録済みURL・短いURL・クリック数・作成日時の一覧 |

テーブル

| テーブル | 主な項目 |
| --- | --- |
| short_urls | id、code（一意）、original_url、created_at、updated_at |
| clicks | id、short_url_id（外部キー）、clicked_at |

## 6. 主要な設計論点

以下は要件定義で確定し、採用理由をREADMEにも記載する。推奨案は叩き台であり、検討の結果変えてよい。

| 論点 | 選択肢 | 推奨案と理由 |
| --- | --- | --- |
| 短縮コードの生成方式 | ランダム文字列 / IDの変換（Base62等） | ランダム6〜8文字。連番が推測されにくい。重複時は再生成し、DBの一意制約で最終的に担保する |
| URLのバリデーション | 形式チェックのみ / スキーム制限あり | http・httpsのみ許可し、javascript: などの危険なスキームを弾く。長さの上限も設ける |
| リダイレクトのステータス | 301 / 302 | 302。301はブラウザにキャッシュされ、2回目以降のクリックを記録できないため |
| クリック記録の方式 | 同期でDB書き込み / キューで非同期 | キューで非同期。転送の応答を遅らせないため |
| 存在しないコードへのアクセス | 404画面 / トップへ転送 | 404を返す。誤ったコードを正常と誤認させないため |
| 短縮URLのドメイン | APIと同じホスト / 別ホスト | ローカルではAPIと同じホスト（例: localhost:8000）とし、設定値で変更可能にする |

## 7. 品質方針

型・テスト・CIの3点で品質を担保し、CIが通らない変更はマージしない。

- 型：PHPは全ファイルで `declare(strict_types=1)` と引数・戻り値の型宣言を行い、Larastanは高めのレベル（最大レベルを目標）で通す。TypeScriptは `strict: true` とし、APIの型はOpenAPIから自動生成する
- テスト：APIごとに正常系・異常系の機能テスト（Pest）を書く。短縮コード生成などのロジックは単体テストで確認する。フロントは主要コンポーネントをVitestでテストする
- 規約：Laravel Pint、ESLint、Prettierで整形とルールを統一する
- 開発フロー：1人でも機能ごとにIssueとブランチを作り、PRを経由してマージする。CIの通過をマージ条件とする

本計画書をもとに、Claude Codeで以下のドキュメントをMarkdownで作成し、リポジトリの `docs/` で管理する。API・画面は1つにつき1ファイルとする。

4. Claude Codeへの依頼時は、本書と関連する設計書を参照させる

## 9. 進め方とスケジュール目安

在職中に無理なく進めるため、MVP完成まで約4〜6週間を目安とする。期間は平日の夜と週末の作業を想定した目安であり、進捗に合わせて調整する。

1. 計画（本書の確定）：数日
2. 設計：要件定義書、方式設計書、DB設計書、API・画面設計書、テスト設計書をClaude Codeで作成し、レビューして確定する（約1週間）
3. 環境構築：Docker、Laravel・Reactの初期化、静的解析・テスト・CIのテンプレート整備（約1週間）
4. 実装：API-01〜03、SCR-01〜02をテストと一緒に実装する（約2〜3週間）
5. 仕上げ：README、スクリーンショット・GIF、構成図の整備（数日）

テンプレート整備（手順3）は今後の小さな個人開発でも使い回す前提で作る。

## 10. リスクと対策

| リスク | 対策 |
| --- | --- |
| 設計書づくりに時間がかかり、実装に入れない | 設計書はMVPの範囲に限定し、将来拡張は一覧への記載だけにとどめる |
| 機能を足したくなり、完成が遠のく | 「2. ゴールと完成の定義」を満たすまで拡張機能に着手しない |
| AI生成のコードや設計を理解しないまま進めてしまう | 設計書と主要なコードは自分でレビューし、設計判断の理由を自分の言葉でREADMEに書く（面接で説明できる状態にする） |
| 本業が忙しく、間が空いて中断する | 機能ごとにIssueを小さく切り、1回の作業で1つ終わる粒度にする |
| 環境構築でつまずく | 環境構築を独立した手順として先に済ませ、テンプレート化する |
